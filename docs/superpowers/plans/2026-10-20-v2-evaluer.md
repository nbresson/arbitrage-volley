# V2 « Évaluer » — plan de réalisation

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal :** livrer la V2 : réserve d'examen, examens officiels (création, composition, inscription, code d'accès, passation en salle avec une seule tentative, clôture, résultats), fiche stagiaire côté formateur (examens officiels et avancement pédagogique), consignes CFA saisies par les formateurs.

**Architecture :** même principe que la V1. Tout ce qui protège une bonne réponse, un code d'accès ou une question de la réserve vit dans la base (RLS + fonctions `security definer`). À l'ouverture, l'examen est **figé** : énoncé, propositions, bonne lettre, thème et règles sont copiés dans `examen_questions`, et la passation ne lit que cette copie. La passation réutilise l'écran d'examen d'entraînement de la V1 : on en extrait un composant commun branché sur deux « sources » (séance d'entraînement, tentative officielle).

**Tech Stack :** inchangée (SvelteKit 3 statique, Svelte 5, Supabase, Vitest). Tests d'intégration contre le projet Supabase **de dev** (`npm run test:integration`).

**Spec :** [docs/superpowers/specs/2026-10-17-plateforme-formation-arbitres-design.md](../specs/2026-10-17-plateforme-formation-arbitres-design.md), § 3, 6, 7, 8 (écrans 3, 4, 5, 11, 12 et « Examen officiel : déroulé »), 9.3, 12. Maquettes : https://claude.ai/artifact/H6CPLUXi29jfN8ujF6MiPZ (`Formateur.dc.html` = fiche stagiaire, `Accueil.dc.html` = bloc convocation, `Resultat.dc.html` = badge « Réussi » et seuil). Plan précédent : [2026-10-18-v1-sentrainer.md](2026-10-18-v1-sentrainer.md).

**Branche :** `v2-evaluer`, créée depuis `v1-sentrainer` (la V1 n'est pas encore fusionnée dans `main`).

## Décisions prises dans ce plan (modifiables)

- **Seuil de réussite** : fixé **par examen**, en nombre de bonnes réponses ; valeur proposée par défaut = 70 % du nombre de questions, arrondi au-dessus (spec § 13.3, décision encore ouverte du comité : un seuil commun se règle en gardant la valeur par défaut).
- **Code d'accès** : 6 chiffres, tiré à l'ouverture, affiché en grand sur des volets (le stagiaire tape au clavier numérique d'une tablette). Les espaces et tirets saisis sont ignorés.
- **Composition** : seules les questions **validées d'usage `reserve_examen`** peuvent entrer dans un examen (spec § 3.3). Aujourd'hui la réserve est vide : les formateurs doivent la rédiger (l'écran le dit).
- **Copie figée** : copie dans `examen_questions` (pas de versionnement). Le stagiaire répond par **lettre** (A–D), jamais par identifiant de proposition.
- **Clôture** : clore un examen termine toutes les tentatives en cours avec les réponses déjà arrivées ; une réponse gardée hors ligne qui arrive après la clôture est refusée.
- **Bascule réserve → entraînement** : permise une fois la question passée dans un examen clos, ou si elle n'a jamais servi ; refusée tant qu'un examen non clos la contient.
- **Consignes CFA** : saisies dans l'application (écran 12) ; une seule édition CFA active ; activer une nouvelle édition marque « à relire » les questions validées liées à l'ancienne, comme le chargeur le fait pour le Casebook.

## Global Constraints

- Toutes les contraintes globales du plan V1 restent valables (français, capitales de phrase, verbes sur les boutons ; tokens de `src/lib/styles/tokens.css` uniquement, valeur nouvelle ajoutée d'abord à DESIGN.md ; polices auto-hébergées ; accessibilité AA ; pas d'IA ; clé `service_role` jamais dans le front).
- Aucune correction affichée **pendant ni après** un examen officiel côté stagiaire : seulement score, réussi / non réussi, seuil et score par thème.
- Un stagiaire ne lit jamais : `examen_codes`, `examen_questions.bonne_lettre`, une question `reserve_examen` (table `questions`), ni la copie figée hors de **sa** tentative en cours.
- Les formateurs ne lisent toujours **jamais** les séances `examen_entrainement` (anti-objectif V1, à ne pas casser en réutilisant les composants).
- **Une seule tentative** par stagiaire et par examen (contrainte d'unicité en base) ; l'heure qui compte est celle du serveur (tolérance de ±2 min sur l'heure annoncée, renvoi hors ligne accepté jusqu'à 15 min après la fin, comme `valider_reponse` en V1).
- Migrations nouvelles uniquement (`supabase/migrations/202610200000NN_nom.sql`) ; une migration appliquée ne se modifie pas. Toute fonction `security definer` : `set search_path = public` ; fonctions internes : `revoke execute … from public, anon, authenticated`.
- Alias `#lib/…` avec extension explicite ; pas de `$env/*` (pièges du HANDOFF).

## Review Focus

1. **Reprise après fermeture du navigateur ou changement d'appareil** pendant un examen officiel : le même code redonne la même tentative, le chronomètre ne repart pas de zéro, les réponses déjà données réapparaissent → tests dans les tâches 3 et 5.
2. **Clôture par le formateur alors qu'un stagiaire a des réponses gardées hors ligne** : la clôture calcule le résultat sur ce qui est arrivé ; les réponses envoyées ensuite sont refusées avec « Cet examen est clos. » et retirées de la file (pas de boucle de renvoi) → tests dans les tâches 2, 3 et 5.
3. **Question de la réserve modifiée, archivée ou basculée vers l'entraînement après l'ouverture** : l'examen ouvert ou passé ne change pas (copie figée), et la bascule est refusée tant que l'examen n'est pas clos → test dans la tâche 2.
4. **Saisie du code** : espaces, tirets, code faux, examen pas encore ouvert, examen clos, stagiaire non inscrit → chacun a son message, aucun ne donne d'indice sur le bon code → tests dans les tâches 3 et 5.
5. **Stagiaire parti sans terminer** (temps écoulé, onglet fermé) : il apparaît « en cours » jusqu'à la clôture, puis « terminé » avec le score de ses réponses arrivées ; un stagiaire inscrit qui n'est jamais venu apparaît « absent » → test dans la tâche 2.
